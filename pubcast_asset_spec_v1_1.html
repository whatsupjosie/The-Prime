PubWorld / Studio Engine

This document defines the technical standards for every asset class in PubCast AI. These are not suggestions. They are the line between a scene that works and one that doesn't.

The core test: can you comfortably place the expected count in a working studio scene alongside everything else? If you hesitate, it's too expensive. Build to leave room.

Numbers in green are working targets. Amber = allowed with justification. Red / ! = hard limit, do not cross.

File Formats
Format Hierarchy
GLB
First and default choice for all browser-facing handoffs. Portable, self-contained, least likely to arrive broken. Geometry, materials, textures, skeleton, and animations in one file.
OBJ
Raw geometry only. Materials in a separate MTL — easy to lose. No skeleton, no animation. Source format only. Convert to GLB before shipping.
FBX
Good pipeline source format. Carries rigging and animation. Not for browser-facing handoff. Binary FBX preferred. Convert to GLB before shipping.
STL
3D print format only. No UV, no rig, no material. Full conversion pipeline required before any production use.

Skeleton Standards
Bone Naming & Skeleton Converter

Bone names are the contract. The program reads names and trusts them — a bone called UpperArm_L is treated as the left upper arm without verification. A mislabeled bone corrupts every animation that touches it. The converter maps incoming skeletons to UE5 names by topology and hierarchy — not by name matching. The user is the last line of defence.

Converter Output States
One state per bone. Only Confirmed mappings apply automatically.
Confirmed
Topology match is unambiguous. Renamed automatically. No user review required.
Likely
Good candidate, not certain. Flagged for user review. Suggested but never applied without approval.
Unmatched
No clear candidate. House bone marked inactive. User may manually assign.
Likely mappings are never applied without explicit user approval. No exceptions.
Unmatched bones go to the inactive pool. A 50-bone skeleton missing finger joints runs correctly because those bones are already optional in the house rig.
UI: incoming and house skeletons shown side by side. Proposed mappings as lines — green confirmed, amber likely, red unmatched. User drags to reassign. User approves. That map is then trusted by the system.
Output: retarget map JSON. Original asset is never modified.
Every retarget map carries a live confidence score updated by Jeremy Cricket across takes. Consistent anomalies degrade confidence and surface to the user.
AI Systems
Kinematic Integrity & AI Observation Chain
Design Principle
No AI system in PubCast has complete context. Each operates within its domain, passes observations rather than conclusions, and defers to the chain above it. The user receives the combined read, not a single verdict. The user decides.
Purfluous — Kinematic Integrity Monitor
Visual and kinematic context only. Watches every frame of every take.
Carries a joint limit table per character class. Every joint has a documented range of motion. Purfluous watches against these limits on every frame.
Character classes carry different limits — trained dancer, fighter, child, office worker, non-human. Purfluous needs to know what kind of body it is watching.
Three response levels: Within range (silent). Approaching limit (watch and wait). Past anatomical limit (pass to Jeremy with context).
Distinguishes injury from non-human: injury is sudden force with surrounding joint compensation. Non-human is smooth, consistent, contextless violation — no cause, no compensation.
When a character is confirmed non-human and nothing reads as malfunction, Purfluous notes it on the avatar's profile and stops flagging for that character.
Every observation is written to the background chat screen log and the black box regardless of whether Purfluous escalates. Nothing is ever silently dismissed.
Observation Chain — Kinematic Anomaly
Purfluous
Detects joint exceeding anatomical range. Scores it. Passes to Jeremy with two specific questions: Is this a human body? and Is anything reading as malfunction?
↓
Jeremy Cricket
Is this a human? — reads character registration. Answers definitively. Is anything malfunctioning? — reads retarget map confidence, session history, anomaly patterns. Gives a qualified answer, not a verdict. Jeremy answers. He does not decide.
↓
Purfluous
Receives both answers. Now has full context: kinematic data + character identity + session history. Decides whether to surface to user and frames the message accordingly.
↓
User
Receives the combined read at a natural break — between takes, after cut, or when asked. Makes the call. Nothing stops a take. Nothing overrides a map. The user decides.

The mislabeling case: a wrong bone name can produce smooth, consistent out-of-range motion with no anomaly history. Jeremy honestly reports no malfunction. Purfluous honestly reports out of human range. Both pieces reach the user together. The user makes the call.
Black Box & Background Chat Log
Nothing is ever silently dismissed
Every observation is written to the black box and background chat screen log regardless of escalation decision. The chain filters what interrupts the user — not what gets remembered.
The black box is the flight recorder. Runs always. Records everything. The authoritative record of what the system knew and when it knew it.
The background chat screen is the human-readable version — always accessible, always honest about everything that passed through the system.
Purfluous's dismissal decisions are auditable from the log. Patterns of systematic mis-scoring show up in the record.
Jeremy can identify patterns across sessions and surface them independently even if Purfluous never escalated the individual events.

LOD levels (LOW / LOW-MED / MED / MED-HIGH / HIGH) are authoring constraints, not render states. Different parts of the same object can mix LOD levels freely. LOW breaks into large cubes at destruction. HIGH shatters into fine wedge and corner pieces.
Source voxel JSON must be kept alongside every baked GLB. The JSON is the source of truth. The GLB is the output artifact.
Large structures should declare pivot groups at authoring time for any section carrying a motion tracker, destruction hinge, or collision separation point.

Submission Requirements
Source Handoff Checklist

Every asset submitted for production must include all of the following:

Source file (Blender, Maya, or equivalent)
Exported GLB (browser-ready, final)
All textures (named, power-of-two)
License or rights confirmation
Preview render (turntable or still)
Rig note (bone count, skeleton type)
Animation list (name, loop Y/N, frame range)
Scale / axis / origin confirmation
Retarget map JSON (sourced avatars only)
Voxel source JSON (voxel objects only)
Seated deformation screenshot (avatars only)
Triangle count and material count declared
An asset submitted without its handoff package is not production-ready regardless of visual quality.
The Scene Test — Applies to Every Asset
Before approving any asset: place the expected count in a working studio scene alongside everything else that would normally be there. If the scene hesitates, stutters, or you think twice before adding the third one, the asset is too expensive. Build to leave room. A beautiful asset that breaks the scene when multiplied is not a production-ready asset.
